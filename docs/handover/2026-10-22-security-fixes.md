## 決定済みの判断

| 項目 | 決定 | 理由 |
|---|---|---|
| 並列の単位 | 触るファイルが重ならない単位で分ける | 別の worktree でも、同じファイルを変えるとマージで衝突するため |
| `server.js` の変更順 | P1 → P4 → P5 の順に直列で行う | #82、#83、#84、#86(項目 3・4)がどれも `src/daemon/server.js` を変えるため |
| `engine-process.js` の変更順 | P2 → P6 の順に直列で行う | #85 と #86(項目 5)がどちらも `src/daemon/engine-process.js` を変えるため |
| #82 の `enginePath` の検証の置き場所 | `src/daemon/config.js` か `src/daemon/server.js` に置き、`engine-process.js` は変えない | P2 と並列に進めるため |
| #86 の PR | 項目ごとに分け、本文は `Refs #86(項目 n)` とする。最後の PR で閉じる | 1 つの Issue に、場所の違う 5 項目があるため |
| マージ | 各担当はマージしない。マージは開発者が行う | グローバルの CLAUDE.md の「作業自走中のルール」による |
| この資料の更新 | まとめ役のセッションだけが行う | 各担当の PR で表を書き換えると、PR どうしが衝突するため |

## 落とし穴

- 監査ではコードを実行していない。各 Issue の「何が起きる」は見込みで、再現は確かめていない。担当は、直す前に単体テストで現象を確かめる。
- 再現に別の OS ユーザーが要る件は、実機での確認を PR の「確認して欲しいポイント」に書く。
- Windows の Bash ツールではバックスラッシュが減る(グローバルの CLAUDE.md「ツールの制約」)。PR の本文は `--body-file` で渡す。
